# Lato Phase 4.0 Report: CLI Executable Independence

## Overall Status

**Partially complete.** The source/package executable split, runtime identity propagation, OpenCode compatibility path, CLI help/completion/error identity, and TUI preference-path isolation are implemented and verified on Linux. Focused regression tests pass.

Native Windows/macOS execution and standalone compiled Lato release packaging remain pending. No commit or push was performed. The active branch remains `lato-development` at `4cf69d5`, and the previously published snapshot remains `db16673`.

## 1. Existing Executable Architecture

Before Phase 4.0, both package commands mapped to the same wrapper:

```json
{
  "bin": {
    "lato": "./bin/opencode",
    "opencode": "./bin/opencode"
  }
}
```

The wrapper located a native `opencode` binary through `OPENCODE_BIN_PATH`, a cached `.opencode` path, a sibling `opencode.exe`, or an installed platform package. It then launched that binary with inherited arguments.

The TUI already had identity-aware state logic:

- `cliScriptName()` derived `lato` or `opencode` from the invocation path.
- `cliPreferenceState()` placed interactive preferences under the selected product directory.
- `tui.ts` and `attach.ts` passed that path into the TUI.

That logic could not reliably distinguish Lato from OpenCode because both package commands ultimately invoked a wrapper named `opencode`, and the wrapper did not propagate an identity marker.

## 2. Previous Shared-Wrapper Problem

The shared wrapper produced two concrete failures:

1. Invoking the `lato` package command still executed `bin/opencode`. The CLI therefore resolved OpenCode identity, and the TUI selected the OpenCode preference path.
2. Windows command shims and other invocation layers could obscure the original command name, making path-based identity unreliable.

A third issue was exposed during implementation: the source package uses `"type": "module"`, so an extensionless launcher using CommonJS `require()` failed under Node 22 with `ReferenceError: require is not defined in ES module scope`.

The fix therefore needed both distinct entry files and reliable identity propagation into the shared runtime.

## 3. New Lato Executable Entry Point

Lato now has its own launcher:

- `packages/opencode/bin/lato` is a Node ESM launcher.
- It loads the shared `packages/opencode/bin/run.cjs`.
- The package mapping is now `"lato": "./bin/lato"`.
- The compiled npm package receives a CommonJS `bin/lato` wrapper generated by `script/publish.ts`.

The shared runner remains responsible for locating and launching the native binary. This keeps platform, architecture, musl/baseline, AVX2, and package-manager resolution in one place while giving each product a distinct executable identity.

The wrapper preserves:

- Arguments passed to the CLI.
- Standard input/output/error.
- Exit codes.
- `SIGINT`, `SIGTERM`, and `SIGHUP` forwarding.
- Existing `OPENCODE_BIN_PATH` override behavior.

## 4. OpenCode Compatibility Entry Point

OpenCode remains available through `packages/opencode/bin/opencode` and the package mapping `"opencode": "./bin/opencode"`.

The compatibility entry point uses the same shared runner and engine but sets `LATO_RUNTIME_IDENTITY=opencode` for the child process. This preserves OpenCode invocation behavior while keeping Lato identity distinct.

The following were intentionally not changed:

- Provider IDs `opencode` and `opencode-go`.
- Provider endpoints, authentication, and model discovery.
- Existing commands, options, and command names.
- Browser and desktop source.
- Root package metadata.
- Translation files.

## 5. Runtime Identity Resolution

Runtime identity now resolves in this order:

1. A valid `LATO_RUNTIME_IDENTITY` value (`lato` or `opencode`).
2. The invoked script name from `argv[1]`.
3. The executable path from `argv[0]` or `process.execPath`.
4. Fallback to `lato`.

Invocation names are normalized for backslashes, `.cmd`, and `.exe` suffixes. Invalid environment values are ignored rather than trusted.

| Invocation                                          | Resolved identity | Interactive state root                               |
| --------------------------------------------------- | ----------------- | ---------------------------------------------------- |
| `lato` wrapper                                      | `lato`            | `${XDG_STATE_HOME:-~/.local/state}/lato/kv.json`     |
| `opencode` wrapper                                  | `opencode`        | `${XDG_STATE_HOME:-~/.local/state}/opencode/kv.json` |
| Compiled `lato`                                     | `lato`            | `lato` state path                                    |
| Compiled `opencode`                                 | `opencode`        | `opencode` state path                                |
| `LATO_RUNTIME_IDENTITY=opencode` on a Lato launcher | `opencode`        | `opencode` state path                                |
| Unrelated source runner                             | `lato`            | `lato` state path                                    |

Unknown invocations do not silently fall back to OpenCode identity.

## 6. TUI State-Path Behavior

TUI state behavior was preserved, not redesigned.

- Interactive preferences remain separate: `lato/kv.json` versus `opencode/kv.json`.
- Explicit theme configuration in shared configuration remains shared by design.
- No preference namespace migration was performed.
- No real user preferences or credentials were read or modified.
- Tests used synthetic temporary directories.

The `TUI` and `attach` commands continue to resolve their state path through `cliPreferenceState(cliScriptName(), Global.Path.state)`. Because the wrappers now propagate identity, Lato and OpenCode reach the correct existing path.

## 7. CLI Branding and Output

Yargs receives the resolved identity through `scriptName`. Verified behavior includes:

- Lato help shows `lato completion`.
- OpenCode help shows `opencode completion`.
- Lato completion uses `###-begin-lato-completions-###`.
- OpenCode completion uses `###-begin-opencode-completions-###`.
- Invalid options exit non-zero and print help using the correct command identity.

Current Lato wordmark and command descriptions remain unchanged for both identities. This preserves existing compatibility output and avoids an unrelated documentation/copy rewrite. Version output also remains unchanged.

## 8. Provider Compatibility

## 10. Platform Status and Limitations

### Linux

Verified natively on Linux x86_64:

- Both source entry points.
- Identity propagation.
- Argument and exit-code pass-through.
- Node-based symlink invocation.
- Help, completion, and invalid-option identity.
- Compiled Lato/OpenCode identity.
- Synthetic preference separation.

### Windows

Prepared but not natively verified:

- Wrapper identity normalizes Windows separators and `.cmd`/`.exe` suffixes.
- Separate `lato` and `opencode` package commands are defined.
- The CI workflow includes focused executable tests.
- Native npm `.cmd` shim behavior, Windows process signaling, and postinstall-generated wrapper behavior remain unverified.

### macOS

Prepared but not natively verified:

- Path and identity behavior is platform-independent in tests.
- No native macOS runner was available.
- Native binary resolution and signal behavior remain unverified.

No Windows or macOS native validation is claimed from Linux results.

## 12. Known Issues

- Native Windows/macOS execution has not been validated.
- The published npm wrapper path is covered by a synthetic test but was not installed from a registry or packed distribution.
- Standalone compiled release artifacts still expose only the compiled `opencode` executable. Lato independence currently applies to source and npm-style package entry points.
- Bun resolves symlinks before exposing the invocation path; symlink-based identity is verified under Node. Normal package entry points use distinct files and do not depend on symlinks.
- OpenCode compatibility help uses OpenCode command/completion identity but retains the current Lato wordmark and Lato-specific command descriptions.
- Version output remains a bare semantic version with no product prefix.
- Root `package.json` retains upstream metadata; translated READMEs remain unchanged.
- `README.md` links to a missing `NOTICE` file. This is a pre-existing publication issue.
- No commit or push was performed. The active branch, tags, remotes, published snapshot, and existing untracked documentation were preserved.

## 13. Recommended Phase 4.1

1. Add a standalone Lato release entry point so compiled distributions expose both `lato` and `opencode` without requiring a Node wrapper.
2. Run native Windows and macOS executable tests, including npm `.cmd` shims and postinstall-generated wrappers.
3. Add an install-from-local-package smoke test in an isolated temporary prefix; do not publish to a registry.
4. Decide whether OpenCode compatibility help should retain Lato copy or gain product-specific error/help text.
5. Add completion coverage for zsh, fish, and PowerShell if those shells remain supported.
6. Resolve ownership of root package metadata, translated READMEs, and the missing `NOTICE` file.
7. Keep TUI preference isolation unchanged while adding an interactive theme-restart assertion if it can run without touching real user state.
